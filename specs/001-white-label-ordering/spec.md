# Feature Specification: 可白牌化智慧餐飲訂單系統平台

**Feature Branch**: `001-white-label-ordering`
**Created**: 2026-01-08
**Status**: Draft
**Input**: 可白牌化智慧餐飲訂單系統平台 - 支援多品牌快速切換、動態菜單引擎、訂餐功能、管理後台與分析報表

## User Scenarios & Testing

### User Story 1 - 品牌快速上線（白牌化核心）(Priority: P1)

管理員需要為一個新餐廳品牌快速建立完整的線上訂餐系統，包括上傳菜單資料、設定品牌視覺風格（Logo、主題色、字體風格），並立即在前端呈現出該品牌獨特的訂餐介面，而不需要修改任何程式碼或重新部署系統。

**Why this priority**: 這是整個平台的核心價值 - 白牌化能力。沒有這個功能，平台就只是單一餐廳系統。這個功能決定了平台是否能成為多品牌服務的基礎。

**Independent Test**: 上傳一個全新品牌的 JSON 菜單檔案（包含品牌視覺設定），系統應立即生成該品牌的訂餐網站，前端能正確顯示品牌 Logo、主題色、菜單項目，且與其他品牌完全獨立運作。

**Acceptance Scenarios**:

1. **Given** 管理員已登入管理後台，**When** 上傳包含完整菜單結構和品牌視覺設定的 JSON 檔案，**Then** 系統解析並儲存菜單資料、視覺設定，並生成該品牌的唯一識別碼和專屬網址
2. **Given** 品牌菜單已上傳成功，**When** 顧客訪問該品牌的專屬網址，**Then** 前端自動套用該品牌的 Logo、主題色、字體風格，並正確顯示該品牌的完整菜單
3. **Given** 系統中已有多個品牌，**When** 管理員更新其中一個品牌的視覺風格（例如更換主題色），**Then** 只有該品牌的前端介面更新，其他品牌不受影響
4. **Given** 管理員上傳新品牌資料，**When** 菜單 JSON 格式不完整或缺少必要欄位，**Then** 系統顯示明確的錯誤訊息，指出具體缺少的欄位和格式要求

---

### User Story 2 - 顧客完整訂餐流程 (Priority: P2)

顧客訪問特定品牌的訂餐網站，瀏覽分類清楚的菜單、選擇餐點並進行客製化設定（如加料、甜度、溫度調整），將商品加入購物車，確認訂單內容並送出訂單，最後取得訂單編號並能追蹤訂單狀態。

**Why this priority**: 這是顧客最核心的使用場景，也是平台的主要收入來源。沒有順暢的訂餐流程，平台就無法產生實際價值。

**Independent Test**: 一位新顧客從進入網站、瀏覽菜單、加入購物車、客製化選項、確認訂單到取得訂單編號，整個流程應能在 3 分鐘內完成，且每個步驟都有清楚的視覺回饋。

**Acceptance Scenarios**:

1. **Given** 顧客進入品牌訂餐網站，**When** 瀏覽菜單，**Then** 看到依分類組織的餐點列表，每個餐點顯示名稱、價格、簡介和圖片（如有）
2. **Given** 顧客選擇特定餐點，**When** 點擊餐點查看詳情，**Then** 顯示可用的客製化選項（加料、甜度、溫度等），並能選擇數量
3. **Given** 顧客已選擇餐點和客製化選項，**When** 加入購物車，**Then** 購物車更新顯示商品數量和總價，且顧客可繼續瀏覽或前往結帳
4. **Given** 顧客在購物車頁面，**When** 確認訂單內容並送出，**Then** 系統生成唯一的訂單編號，顯示訂單摘要，並提供訂單編號供後續查詢
5. **Given** 顧客已送出訂單，**When** 使用訂單編號查詢，**Then** 顯示訂單狀態（如：已接單、準備中、已完成）和預計完成時間

---

### User Story 3 - 管理員營運數據分析 (Priority: P3)

管理員登入專屬的管理後台，查看即時和歷史的營運數據，包括營收統計、訂單數量趨勢、熱銷品項排行、不同時段的訂單分布，透過視覺化圖表快速掌握營運狀況，並能匯出報表供決策參考。

**Why this priority**: 數據分析能幫助餐廳管理者做出更好的營運決策，但不是訂餐系統能運作的必要條件，因此優先級次於訂餐核心功能。

**Independent Test**: 管理員登入後能看到過去 30 天的營收圖表、今日熱銷前 10 名商品、以及各時段訂單分布，所有數據能在 2 秒內載入完成。

**Acceptance Scenarios**:

1. **Given** 管理員已登入並擁有 admin 權限，**When** 進入 Analytics 頁面，**Then** 顯示營收統計、訂單趨勢圖表和熱銷品項排行
2. **Given** 管理員在 Analytics 頁面，**When** 選擇時間區間（如：今日、本週、本月、自訂區間），**Then** 圖表和數據更新為該時間區間的統計結果
3. **Given** 管理員查看熱銷品項，**When** 點擊特定品項，**Then** 顯示該品項的詳細銷售數據（銷售數量、營收貢獻、顧客評價等）
4. **Given** 管理員需要報表，**When** 點擊匯出按鈕，**Then** 系統生成 CSV 或 PDF 格式的報表供下載

---

### User Story 4 - 品牌與權限管理 (Priority: P4)

平台管理員（super admin）能夠建立和管理多個品牌帳號，為每個品牌指派獨立的管理員帳號，各品牌管理員只能存取和管理自己品牌的菜單、訂單和數據，無法看到其他品牌的資訊，確保資料安全和隱私。

**Why this priority**: 多品牌管理是白牌化平台的重要功能，但可以在核心訂餐和單一品牌功能穩定後再實作。

**Independent Test**: 建立兩個品牌（Brand A 和 Brand B），各自指派一位管理員。Brand A 管理員登入後應只能看到 Brand A 的菜單、訂單和數據，無法存取 Brand B 的任何資訊。

**Acceptance Scenarios**:

1. **Given** Super admin 已登入，**When** 建立新品牌並指派管理員帳號，**Then** 該管理員可使用帳號密碼登入，並只能存取該品牌的管理功能
2. **Given** 品牌管理員已登入，**When** 嘗試存取其他品牌的資料（透過 URL 或 API），**Then** 系統拒絕存取並回傳權限不足的錯誤訊息
3. **Given** Super admin 查看平台總覽，**When** 檢視所有品牌列表，**Then** 顯示每個品牌的基本資訊、管理員帳號、活躍狀態和訂單數量摘要

---

### User Story 5 - AI 擴充預留接口 (Priority: P5)

系統預留標準化的 AI 模組接口，讓未來能輕鬆整合菜單推薦、使用者偏好分析、銷售預測等 AI 功能，而不需要大幅修改現有系統架構。目前階段僅需要定義接口規格和回傳模擬資料的 stub 實作。

**Why this priority**: AI 功能是未來增值服務，但不是目前 MVP 的必要功能。此階段只需確保架構支援未來擴充，不需實作真實的 AI 邏輯。

**Independent Test**: 呼叫 AI 推薦 API 接口，系統回傳符合預定義格式的模擬推薦結果（如：前 3 名推薦商品清單），驗證接口規格完整且可用。

**Acceptance Scenarios**:

1. **Given** 系統已定義 AI 推薦接口規格，**When** 前端呼叫推薦 API，**Then** 後端回傳符合規格的模擬資料（包含推薦商品 ID、名稱、推薦原因）
2. **Given** 未來整合真實 AI 模型，**When** 替換 stub 實作為真實 AI 邏輯，**Then** 前端和其他模組無需修改即可使用新的 AI 功能

---

### Edge Cases

- **菜單資料不完整**：當品牌上傳的 JSON 缺少必要欄位（如品牌名稱、主題色、菜單項目）時，系統如何處理？應明確指出錯誤並拒絕上傳。
- **品牌唯一識別衝突**：如何確保每個品牌的識別碼（ID 或 slug）是唯一的？系統應自動檢查並防止重複。
- **訂單高峰時段**：當多個品牌同時湧入大量訂單時，系統如何維持效能和回應速度？需要設計合理的負載處理機制。
- **客製化選項組合**：當顧客選擇的客製化選項超過允許範圍（如選擇了互斥的選項）時，系統如何驗證和提示？
- **品牌主題色極端值**：當品牌設定的主題色是極淺或極深的顏色（對比度不足）時，系統如何確保文字可讀性？
- **訂單查詢安全性**：如何防止惡意使用者透過遍歷訂單編號來查看他人的訂單？需要額外的驗證機制。
- **管理員權限提升**：如何防止品牌管理員嘗試提升自己的權限或存取其他品牌資料？需要嚴格的權限檢查。
- **品牌停用或刪除**：當品牌被停用或刪除時，該品牌的歷史訂單和數據如何處理？應保留歷史記錄但停止新訂單。

## Requirements

### Functional Requirements

**白牌化核心功能**

- **FR-001**: 系統必須支援透過 JSON 格式上傳完整的品牌菜單資料，包括品牌資訊、視覺風格設定和菜單結構
- **FR-002**: 系統必須為每個品牌生成唯一的識別碼和專屬訂餐網址
- **FR-003**: 前端必須能根據品牌識別碼動態載入並套用該品牌的 Logo、主題色、輔助色和字體風格
- **FR-004**: 系統必須驗證上傳的 JSON 格式完整性，並在格式錯誤時提供具體的錯誤訊息
- **FR-005**: 品牌菜單和視覺風格的更新必須即時反映在前端，無需重新部署或重啟服務

**菜單結構與客製化**

- **FR-006**: 系統必須支援階層式的菜單結構（分類 > 品項）
- **FR-007**: 每個菜單品項必須包含名稱、價格、簡介、圖片 URL（選填）
- **FR-008**: 系統必須支援品項的客製化選項，包括：加料項目、甜度選擇、溫度選擇
- **FR-009**: 客製化選項必須能設定額外價格和互斥規則（如某些選項不能同時選擇）

**訂餐功能**

- **FR-010**: 顧客必須能瀏覽品牌的完整菜單，並依分類篩選品項
- **FR-011**: 顧客必須能選擇品項、設定客製化選項、選擇數量並加入購物車
- **FR-012**: 購物車必須即時顯示商品列表、各項價格和總金額
- **FR-013**: 顧客必須能在購物車中修改商品數量、客製化選項或移除商品
- **FR-014**: 顧客確認訂單後，系統必須生成唯一的訂單編號（格式如：CC20260108-0001）
- **FR-015**: 系統必須記錄每筆訂單的完整資訊：訂單編號、品牌、商品清單、客製化選項、總金額、時間戳記
- **FR-016**: 顧客必須能使用訂單編號查詢訂單狀態和詳細內容

**訂單狀態管理**

- **FR-017**: 系統必須支援至少 4 種訂單狀態：已接單、準備中、已完成、已取消
- **FR-018**: 訂單狀態變更必須記錄時間戳記和操作者（如為系統自動更新或由工作人員手動更新）

**權限與安全**

- **FR-019**: 系統必須支援至少 3 種角色：顧客（customer）、工作人員（staff）、管理員（admin）
- **FR-020**: 管理員必須能存取完整的管理後台和 Analytics 頁面
- **FR-021**: 工作人員必須能管理訂單狀態，但無法存取 Analytics 和品牌設定
- **FR-022**: 顧客無需註冊或登入即可瀏覽菜單和送出訂單，但需訂單編號才能查詢訂單
- **FR-023**: 所有管理後台和 Analytics API 必須驗證使用者的 JWT Token 和角色權限
- **FR-024**: 系統必須防止跨品牌的資料存取（品牌 A 的管理員無法看到品牌 B 的資料）

**Analytics 與報表**

- **FR-025**: Analytics 頁面必須顯示營收統計，包括總營收、平均客單價
- **FR-026**: Analytics 頁面必須顯示訂單趨勢圖表，支援按日、週、月統計
- **FR-027**: Analytics 頁面必須顯示熱銷品項排行（前 10 名），包括銷售數量和營收貢獻
- **FR-028**: Analytics 頁面必須顯示時段分析（如：各小時的訂單數量分布）
- **FR-029**: Analytics 數據必須能匯出為 CSV 或 PDF 格式

**AI 擴充預留**

- **FR-030**: 系統必須定義標準化的 AI 推薦 API 接口規格（輸入：使用者 ID / 訂單歷史，輸出：推薦商品清單）
- **FR-031**: 目前階段 AI 推薦 API 必須回傳符合規格的模擬資料（stub implementation）
- **FR-032**: AI 模組的實作必須能在不修改前端和業務邏輯的情況下替換為真實的機器學習模型

### Key Entities

- **Brand（品牌）**: 代表一個餐廳品牌，包含品牌名稱、唯一識別碼（slug）、Logo URL、主題色、輔助色、字體風格
- **Category（分類）**: 菜單的分類，如「主餐」、「飲料」、「甜點」，屬於特定品牌
- **MenuItem（菜單品項）**: 具體的餐點或商品，包含名稱、價格、簡介、圖片、所屬分類
- **CustomizationOption（客製化選項）**: 品項的可選配置，如加料、甜度、溫度，包含選項名稱、額外價格、互斥規則
- **Order（訂單）**: 顧客的完整訂單，包含訂單編號、品牌、訂單商品清單、總金額、狀態、建立時間
- **OrderItem（訂單商品）**: 訂單中的單一商品項目，包含品項參照、數量、客製化選項、小計
- **User（使用者）**: 系統使用者，包含帳號、密碼、角色（customer / staff / admin）、所屬品牌（如為品牌管理員）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 管理員能在 10 分鐘內完成新品牌的菜單上傳和視覺風格設定，並在前端看到完整的訂餐網站
- **SC-002**: 顧客能在 3 分鐘內完成從瀏覽菜單、選擇商品、客製化設定到送出訂單的完整流程
- **SC-003**: 系統同時支援至少 3 個不同品牌運作，各品牌的訂單、數據和視覺風格完全獨立，互不干擾
- **SC-004**: 品牌視覺風格（主題色、Logo）的更新能在 5 秒內反映在前端，無需重新部署
- **SC-005**: Analytics 頁面的所有圖表和數據能在 2 秒內載入完成，即使資料庫包含 10,000 筆訂單
- **SC-006**: 系統能在尖峰時段（每分鐘 100 筆訂單）維持正常運作，訂單回應時間不超過 3 秒
- **SC-007**: 品牌管理員嘗試存取其他品牌資料時，系統 100% 攔截並回傳權限錯誤，無任何資料洩漏
- **SC-008**: 顧客使用訂單編號查詢時，能在 1 秒內取得訂單狀態和詳細內容
- **SC-009**: AI 推薦 API 的 stub 實作能在 500ms 內回傳模擬推薦結果，且格式符合預定義規格
- **SC-010**: 開發團隊能在不修改前端程式碼的情況下，將第三方餐廳的菜單 JSON 匯入系統並立即上線

## Assumptions

- 顧客在送出訂單時不需要登入或註冊，但需要提供聯絡方式（如電話或姓名）供餐廳確認訂單
- 系統初期不支援線上付款，訂單為「到店取餐」或「現場付款」模式
- 品牌的菜單 JSON 由品牌管理員自行準備，系統不提供圖形化的菜單編輯器（此階段僅支援 JSON 上傳）
- Analytics 頁面的數據為即時計算，不需要預先產生報表或使用快取（效能優化可在後續版本處理）
- 系統部署在 Zeabur 雲端平台，PostgreSQL 資料庫由 Zeabur 提供和管理
- 前端使用現代瀏覽器（Chrome、Firefox、Safari、Edge 最新版本），不需支援 IE11
- 品牌的 Logo 和菜單圖片由品牌管理員自行託管（如使用 Imgur、Cloudinary 等圖床），系統僅儲存圖片 URL
- 訂單狀態更新由工作人員手動操作，系統不自動更新訂單狀態（如根據時間自動完成訂單）

## Dependencies

- **Zeabur 雲端平台**：系統部署和執行環境
- **PostgreSQL 資料庫**：資料儲存和查詢
- **圖床服務（外部）**：品牌 Logo 和菜單圖片的託管服務（如 Imgur、Cloudinary）
- **前端技術棧**：React + Headless UI（或 Radix UI）+ Tailwind CSS（使用 Vite 建構）。選擇理由：白牌化需要動態 UI 調整，Headless UI 提供無樣式的可存取行為層，Tailwind CSS 支援 Theme Token / Style DSL 實現 data-driven UI，避免傳統 UI Framework 的風格綁定問題
- **JWT 函式庫**：用於產生和驗證身份驗證 Token

## Out of Scope

- 線上付款整合（如信用卡、電子錢包）
- 外送物流整合（如 Uber Eats、Foodpanda）
- 顧客帳號系統和會員功能（如會員點數、優惠券）
- 即時訂單通知（如推播通知、簡訊通知）
- 多語系支援（初期僅支援繁體中文）
- 圖形化菜單編輯器（品牌管理員需自行準備 JSON 檔案）
- 真實的 AI 推薦模型訓練和整合（此階段僅預留接口和 stub 實作）
- 效能監控和日誌分析工具整合（如 Sentry、DataDog）
